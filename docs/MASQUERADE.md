# Hysteria2 Masquerade — управление, подбор апстрима и мониторинг

Этот документ описывает подсистему `core/masquerade/`: зачем она нужна, как
устроена, как её настраивать и как безопасно разворачивать на боевом сервере.

---

## 1. Что такое masquerade и чем он не является

Hysteria2 — это HTTP/3-сервер. Клиент, который не прошёл авторизацию,
получает обычный HTTP-ответ. Что именно отдать такому посетителю — решает
секция `masquerade` в конфигурации сервера.

Три вещи, которые легко перепутать, и в этом проекте они **строго
независимы**:

| Домен | Что это | Кто управляет |
| --- | --- | --- |
| **TLS / SNI** | сертификат *этого* сервера на `ACME_DOMAIN` | ACME внутри Hysteria2, `install.sh`, `hyvpn cert` |
| **Masquerade** | что сервер показывает неавторизованному HTTP-клиенту | `hyvpn masquerade` (этот документ) |
| **REALITY** | механизм Xray, в Hysteria2 отсутствует | не применимо |

Практические следствия:

- `masquerade.proxy.url` — это **источник контента на стороне сервера**, а не
  SNI клиента и не «dest» из REALITY. Менять апстрим = не менять TLS.
- Клиентские ссылки `hysteria2://...?sni=...` от masquerade не зависят и при
  смене апстрима не меняются. Пользователям не нужны новые ключи.
- **Нельзя** «подставить Google в SNI». В этом проекте такой возможности нет
  ни в одном слое: домен берётся из `ACME_DOMAIN`, ссылки строятся из
  `SERVER_DOMAIN`, а генератор конфигурации не содержит поля SNI вообще.
- `insecure=true` не используется как обход проблем: upstream-сертификат
  проверяется всегда, `masquerade.proxy.insecure` жёстко `false`.
- `sniGuard` не отключается: валидатор отвергает `disable`.

## 2. Аудит: откуда взялся «Google» в masquerade

Проверка репозитория (коммиты и все файлы):

```
git log --all -S "google" --oneline     # пусто
git grep -i "masquerade" $(git rev-list --all)
```

Результат:

- В репозитории **нет** ни одного упоминания `google` и ни одной секции
  `masquerade` со значением. Шаблон `hysteria-server.yaml` до этого PR вообще
  не содержал masquerade и заканчивался комментарием «No masquerade is
  required by the specification».
- `install.sh` не писал и не писал бы `masquerade: proxy: url: ...`.
- `render_hysteria_config.py` подставлял только три переменные
  (`TRAFFIC_STATS_SECRET`, `ACME_DOMAIN`, `ACME_EMAIL`) — masquerade в
  генерации не участвовал.
- В `systemd/hysteria-server.service` `ExecStart` указывал на
  `/run/hyvpn/hysteria-server.yaml`, который пересобирался из шаблона при
  каждом старте.

Вывод: **«Google» не является частью репозитория**. Это либо правка боевого
`/run/hyvpn/hysteria-server.yaml` (она молча терялась при следующем
перезапуске), либо правка `/opt/hyvpn/hysteria-server.yaml` на сервере
(переживала обновление только до следующего `install.sh`), либо отдельный
юнит/конфиг вне этого проекта.

Проверить на конкретном сервере можно одной командой (только чтение):

```bash
sudo hyvpn masquerade doctor
```

Она покажет, какой файл реально описывает masquerade, что в нём указано и
входит ли апстрим в реестр кандидатов. Если апстрим чужой, в отчёте будет
предупреждение «deployed upstream ... is not in the candidate registry».

Почему чужой домен — плохая идея: это перекладывание чужого трафика на
третью сторону без разрешения, зависимость от чужой доступности и
невозможность влиять на содержимое. По умолчанию реестр кандидатов **пуст**,
и сервер отдаёт собственный локальный сайт.

## 3. Архитектура

```
hysteria-server.yaml (шаблон, listen/acme/auth/trafficStats)
        │  ${MASQUERADE_YAML}
        ▼
/etc/hyvpn/masquerade.fragment.yaml   ← пишет только `hyvpn masquerade` (root)
        │  bin/render_hysteria_config.py (ExecStartPre, пользователь hysteria)
        ▼
/run/hyvpn/hysteria-server.yaml (0600)  →  hysteria server -c …
```

- Фрагмент — отдельный файл, поэтому смена апстрима это одна атомарная
  операция (`os.replace`) и один перезапуск юнита.
- Рендерер подставляет фрагмент и при ошибке берёт последний рабочий
  (`masquerade.fragment.last-good.yaml`), а если и тот плох — секцию убирает.
  Сломанный masquerade никогда не мешает VPN подняться.

Модули `core/masquerade/`:

| Файл | Ответственность |
| --- | --- |
| `models.py` | типы: `Candidate`, `ProbeResult`, `Evaluation`, `Thresholds` |
| `config.py` | `masquerade.json`, пути, валидация конфигурации |
| `state.py` | `/var/lib/hyvpn/masquerade/state.json`: история проб, активный кандидат, решения |
| `probe.py` | реальная HTTPS-проверка апстрима (DNS → TCP → TLS → HTTP → контент) |
| `scoring.py` | детерминированная оценка по истории проб |
| `selector.py` | решение: оставить, переключить, уйти в локальный fallback |
| `deploy.py` | транзакционное применение: backup → render → validate → atomic → restart → verify → rollback |
| `site.py` + `site/` | локальный статический сайт-fallback |
| `capabilities.py` | что умеет установленный бинарник (версия, `check`, ECH/obfs) |
| `diagnostics.py` | read-only отчёт о среде (без секретов) |
| `requests.py` | очередь «бот → root» через каталог + systemd `.path` |
| `engine.py` | оркестрация всего перечисленного |
| `cli.py` | команды `hyvpn masquerade …` |

## 4. Конфигурация

`/etc/hyvpn/masquerade.json` (создаётся установщиком, правится руками или
командами `candidates`):

```json
{
  "version": 1,
  "mode": "auto",
  "candidates": [
    {
      "id": "own-site",
      "url": "https://vpn.example.com/",
      "enabled": true,
      "priority": 10,
      "description": "own static site"
    }
  ],
  "thresholds": {
    "min_score": 0.55,
    "min_samples": 3,
    "window": 10,
    "min_availability": 0.8,
    "latency_good_ms": 400,
    "latency_bad_ms": 2500,
    "probe_attempts": 2,
    "retry_delay_seconds": 0.5,
    "failover_after_failures": 1,
    "switch_margin": 0.15,
    "switch_confirmations": 3
  },
  "proxy": { "rewriteHost": true, "xForwarded": false },
  "string": {
    "content": "<!doctype html>…",
    "headers": { "content-type": "text/html; charset=utf-8" },
    "statusCode": 200
  },
  "fallback": { "index": "index.html" }
}
```

Режимы:

| `mode` | Поведение |
| --- | --- |
| `auto` | движок сам выбирает `proxy` (лучший проверенный апстрим) или `file` (локальный сайт) |
| `proxy` | только апстрим; если ни один не прошёл проверку — конфигурация **не меняется** и пишется ошибка |
| `file` | всегда локальный сайт |
| `string` | фиксированный ответ (`string.content/headers/statusCode`) |
| `none` | секции masquerade нет, все HTTP-запросы получают 404 |

`proxy.insecure` невозможно включить через конфиг: `from_json` отвергает
`true`, а валидатор — тоже.

Полная схема эмитируемых полей — только документированные Hysteria2:

```yaml
masquerade:
  type: proxy            # proxy | file | string
  proxy:
    url: https://example.org/
    rewriteHost: true
    insecure: false
    xForwarded: false
  file:
    dir: /var/lib/hyvpn/masquerade/site
  string:
    content: hello
    headers: { content-type: text/html; charset=utf-8 }
    statusCode: 200
```

`listenHTTP`/`listenHTTPS`/`forceHTTPS` намеренно не управляются: TCP/80 на
этом сервере занят ACME HTTP-01, а совмещение требует отдельного решения
администратора.

## 5. Кандидаты: правила

- Только домены, которыми владеет администратор, или апстримы, для которых
  проксирование разрешено. Никакого обхода чужих сайтов «для маскировки».
- Никакого сканирования интернета, генерации случайных имён и CIDR-обхода —
  этого нет в коде и не будет.
- `RealiTLScanner` не используется и не нужен: он ищет **чужие** TLS-хосты для
  REALITY, а здесь нужен свой/разрешённый HTTPS-сайт.
- Апстрим обязан быть `https://`, с валидным сертификатом и обычным HTML.
- `localhost`, приватные, link-local, multicast, reserved и служебные адреса
  отвергаются **до** подключения; подключение идёт на уже проверенный IP, а не
  на повторно разрешённое имя (защита от DNS-rebinding).

Добавление:

```bash
sudo hyvpn masquerade candidates add https://vpn.example.com/ --id own-site
sudo hyvpn masquerade candidates test
sudo hyvpn masquerade optimize --apply
```

## 6. Проверки, оценка, гистерезис

Одна проба (`probe.py`) делает:

1. синтаксис URL (только `https`, без креденшелов и фрагментов);
2. DNS с таймаутом;
3. отсев запрещённых адресов;
4. TCP-соединение с таймаутом;
5. TLS с проверкой цепочки и hostname (`ssl.create_default_context()`);
6. `GET` запроса с бюджетом времени;
7. переходы по редиректам (не более `max_redirects`, детект петель);
8. статус 2xx, `Content-Type` из списка, минимальный размер тела, наличие
   HTML-маркера;
9. замеры DNS / TCP / TLS / TTFB / total.

TCP-коннект или TLS-хендшейк сами по себе **никогда** не делают кандидата
здоровым: `ok=true` выставляется только после успешного HTTP-обмена с
осмысленным телом.

Оценка — взвешенная сумма (веса настраиваются):

| Фактор | Что измеряет |
| --- | --- |
| TLS | доля проб без TLS-ошибок в окне |
| HTTP | доступность (`successes / samples`) |
| latency | средняя задержка, линейно между `latency_good_ms` и `latency_bad_ms` |
| stability | разброс задержек (коэффициент вариации) |
| redirects | стабильность цепочки редиректов |

Здоровым (`healthy`, пригоден для выбора) кандидат становится только если:
последняя проба `ok`, набрано `min_samples` проб, доступность ≥
`min_availability`, score ≥ `min_score`, цепочка редиректов не «пляшет».

Гистерезис:

- **Failover быстрый**: внутри цикла проба повторяется `probe_attempts` раз;
  если цикл всё равно провален — `consecutive_failures` растёт, и при
  `failover_after_failures` (по умолчанию 1) движок уходит на лучший
  альтернативный апстрим, а если такого нет — на локальный сайт.
- **Оптимизация медленная**: замена рабочего апстрима на более быстрый требует
  лидерства по score ≥ `switch_margin` в течение `switch_confirmations`
  циклов подряд (по умолчанию 3 × 15 мин). Один удачный замер ничего не решает.
- `optimize --dry-run` не увеличивает счётчик подтверждений, поэтому «посмотреть
  предложение» не ускоряет переключение.

## 7. CLI

Все команды доступны как `hyvpn masquerade …` (обёртка запускает их от root,
потому что они читают `/etc/hyvpn` и могут перезапускать юнит). Эквивалент без
обёртки: `sudo /opt/hyvpn/.venv/bin/python /opt/hyvpn/hy-cli.py masquerade …`.

```bash
hyvpn masquerade status              # режим, апстрим, здоровье, сертификат, fallback
hyvpn masquerade check               # диагностика, ничего не меняет
hyvpn masquerade doctor              # среда: ОС, версия hysteria, пути, порты, SAN
hyvpn masquerade candidates list
hyvpn masquerade candidates test     # реальные проверки всех включённых
hyvpn masquerade optimize --dry-run  # предложение без применения
hyvpn masquerade optimize --apply    # применить после подтверждения
hyvpn masquerade set-mode file|proxy|none|string|auto
hyvpn masquerade init                # создать конфиг + сайт + начальный фрагмент
hyvpn masquerade upgrade             # основная команда развёртывания
```

`--json` поддерживается у всех команд. Коды возврата: `0` — успех, `1` —
ошибка/откат, `2` — ошибка использования.

## 8. Telegram

В разделе «Сервер» появилась кнопка «🕸 Маскарад» (и команда `/masq`).
Показывается: режим, апстрим, здоровье, последняя проверка, сертификат,
готовность fallback. Действия: проверить, протестировать кандидатов,
оптимизировать (показать план), применить, посмотреть список кандидатов и
последние применения.

Ограничения по правам:

- бот отвечает только ID из `ALLOWED_TG_IDS` (`WhitelistMiddleware`), а это
  администраторы сервера; подписчики VPN с ботом не взаимодействуют вообще;
- бот работает под `hyvpn` и **не может** писать `/etc/hyvpn` или
  перезапускать юниты. «Применить» ставит запрос в
  `/var/lib/hyvpn/masquerade/requests/`, а применяет
  `hy-masqapply.service` (root) по `hy-masqapply.path`. Формат запроса
  фиксирован — shell-команду через него передать нельзя;
- долгие проверки выполняются в отдельном потоке (`asyncio.to_thread`), цикл
  событий не блокируется, зависшая проверка ограничена таймаутами.

## 9. Мониторинг и failover

- `hy-masqwatch.timer` + `hy-masqwatch.service` (oneshot, root): раз в 15 минут
  пробует активный апстрим и альтернативы, считает score, при необходимости
  применяет новую конфигурацию.
- Перезапуск Hysteria происходит **только** при фактическом изменении
  фрагмента: сравнение идёт по отрендеренному тексту, а не по «была проверка».
- Решения пишутся в журнал юнита и в JSONL
  `/var/lib/hyvpn/masquerade/decisions.log`.
- Блокировка (`flock`) не даёт таймеру и ручной команде применять
  конфигурацию одновременно.

## 10. Развёртывание на сервере (без доступа разработчика)

1. Обновиться на PR-ветку:

   ```bash
   sudo hyvpn update            # или:
   sudo bash <(curl -fsSL https://raw.githubusercontent.com/<owner>/hyvpn-tg/<ref>/install.sh) --yes
   ```

   Установщик идемпотентен: создаст `masquerade.json` (пустой реестр), локальный
   сайт и начальный фрагмент `file`, не трогая базу, ключи, домен и сертификат.

2. Посмотреть среду (только чтение):

   ```bash
   sudo hyvpn masquerade doctor
   sudo hyvpn masquerade upgrade --read-only
   ```

3. Посмотреть план без изменений:

   ```bash
   sudo hyvpn masquerade upgrade --dry-run
   ```

4. Применить (спросит подтверждение; `--yes` для неинтерактивного запуска):

   ```bash
   sudo hyvpn masquerade upgrade
   ```

   Что произойдёт: backup фрагмента → рендер полного YAML → структурная
   валидация (+ `hysteria check`, если бинарник его умеет) → атомарная замена
   фрагмента → `systemctl restart hysteria-server` (только если конфигурация
   реально изменилась) → проверка юнита и содержимого `/run/hyvpn/…` →
   HTTP/3-проверка, если на хосте есть curl с HTTP/3 → при любой ошибке
   автоматический откат и перезапуск.

5. Добавить апстримы (по одному, только свои/разрешённые):

   ```bash
   sudo hyvpn masquerade candidates add https://vpn.example.com/ --id own-site
   sudo hyvpn masquerade candidates test
   sudo hyvpn masquerade optimize --apply
   ```

6. Убедиться:

   ```bash
   sudo hyvpn masquerade status
   sudo hyvpn masquerade check
   sudo systemctl status hy-masqwatch.timer hy-masqapply.path
   ```

## 11. Откат

- Автоматический: любая ошибка применения возвращает предыдущий фрагмент из
  `/var/lib/hyvpn/masquerade/backups/` и перезапускает юнит.
- Ручной: `sudo hyvpn masquerade set-mode file` (локальный сайт) или `none`
  (поведение как до обновления — 404 на HTTP), затем при необходимости
  `sudo cp /var/lib/hyvpn/masquerade/backups/fragment-<ts>.yaml
  /etc/hyvpn/masquerade.fragment.yaml && sudo hyvpn restart hysteria`.
- Полный откат обновления: старый `install.sh` игнорирует фрагмент (в старом
  шаблоне нет плейсхолдера), поэтому достаточно вернуться на предыдущую
  версию — база, ключи и сертификат не затрагивались.

## 12. ECH и обфускация: что выяснено

Проверено по официальной документации Hysteria2 (Full Server Config,
актуальная на момент PR):

- **ECH** сервером поддерживается: `ech.keyPath` с ключом, созданным
  `sing-box generate ech-keypair <public_name>`; сервер печатает в лог список
  конфигураций, который клиенты должны указать в `tls.ech`. Это **не**
  masquerade и не заменяет его.
  Решение проекта: автоматически **не включать**. Причины: нужен отдельный
  ключ, ручная настройка каждого клиента (не все клиенты Hysteria2 умеют
  `tls.ech`), а ошибка конфигурации ломает подключение. `hyvpn masquerade
  doctor` показывает `features.ech: null` — «не проверено этим билдом, не
  включается». Ручной сценарий и откат описаны в официальной документации:
  добавить `ech.keyPath`, раздать клиентам `tls.ech`, при откате убрать оба.
- **Обфускация**: `salamander` (стабильно) и `gecko` (экспериментально,
  `minPacketSize`/`maxPacketSize`, только для handshake-пакетов). Официальная
  документация прямо говорит: при включении сервер перестаёт быть корректным
  HTTP/3-сервером, то есть **masquerade теряет смысл**. Поэтому обфускация не
  включается автоматически и не управляется этим модулем; в отчёте
  `doctor` поля `obfs_*` имеют значение `null` (не проверено), а не выдуманное
  «поддерживается с версии X».
- **Проверка конфигурации бинарником**: отдельная команда `check` есть не во
  всех сборках. Она определяется по выводу `hysteria --help`; если её нет,
  конфигурация проверяется структурно (YAML + схема полей) и затем — фактом
  успешного запуска юнита. Никакая «своя» команда валидации не выдумывается.
- **HTTP/3-проверка** выполняется только если `curl -V` сообщает о поддержке
  HTTP/3 (используется `--http3-only` при наличии, иначе `--http3`, всегда с
  проверкой сертификата). Результат учитывается как критерий отката только
  если такая же проверка проходила **до** изменения: на части хостов нет
  hairpin-доступа к собственному публичному UDP/443.

## 13. Что проверено локально, а что нужно проверить на VPS

Проверено локально (юнит-тесты, сеть замокана):

- синтаксис/безопасность URL, DNS-таймаут и ошибки, отказ для приватных и
  loopback-адресов, несовпадение имени в сертификате, истёкший сертификат;
- редиректы, петли, лимит переходов, 403/404/500, таймауты, мусорный
  `Content-Type`, слишком короткое тело;
- score, порядок ранжирования, consecutive failures, восстановление после
  сбоя, гистерезис переключения, активация fallback;
- персистентность состояния между запусками, устойчивость к битому JSON;
- валидация YAML (неизвестные поля, отсутствие masquerade, `insecure: true`,
  `sniGuard: disable`, чужой `acme.domains`);
- атомарное обновление, отсутствие перезапуска при отсутствии изменений,
  откат при провале проверки после рестарта, режимы файлов 0640/0600;
- рендерер: подстановка фрагмента, fallback на last-good, совместимость со
  старым поведением;
- CLI-команды (dry-run не пишет конфиг), очередь запросов бота и права;
- бот: экран маскарада, кнопки, отсутствие доступа у посторонних.

Требует проверки на живом сервере (по определению не воспроизводится в CI):

- реальный выпуск/валидность сертификата и `sniGuard` на боевом домене;
- реальная доступность выбранного апстрима из сети VPS;
- HTTP/3-проверка (`curl --http3`) и hairpin NAT;
- поведение `hysteria check` на конкретной установленной версии;
- перезапуск юнита и отсутствие рестартов при неизменной конфигурации;
- systemd `.path`-триггер (`hy-masqapply.path`) в реальном systemd.

## 14. Ограничения

- Реестр кандидатов — файл на сервере, без внешней базы и без API.
- Движок пробует не более 8 кандидатов за цикл.
- «Похожесть на сайт» не защищает от активного анализа трафика — это задача
  обфускации, а не masquerade.
- Локальный сайт — статический; динамики и внешних ресурсов в нём нет
  намеренно (fallback обязан работать без интернета).
